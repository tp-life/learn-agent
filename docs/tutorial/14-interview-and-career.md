## 一、概念详解：求职的六个底层认知

### 1.1 简历项目段落的黄金结构：问题 → 架构决策 → 量化结果

面试官筛一份简历平均只有几十秒，项目段落必须三句话内立住：

1. **问题**：解决什么真实痛点，一句话，让非专家也能懂；
2. **架构决策**：1-2 个关键技术取舍及原因——体现判断力，不是堆砌名词；
3. **量化结果**：可度量的数字（recall@5、p99 延迟、token 成本下降比例……）。

**反例**："熟悉 LangChain、向量数据库、LLM、RAG、Agent……"——罗列技术栈等于告诉面试官"我背过名词"。三个问题立刻露馅：你做过什么？怎么做决策的？效果如何？一个都答不上。

同一段经历的两种写法对比：

- 差："负责 RAG 系统开发，熟悉 embedding、向量数据库、混合检索。"
- 好："面向企业文档问答场景实现端到端 RAG 系统；针对错误码类字面查询召回差的问题，引入向量 + BM25 混合检索（RRF 融合），recall@5 从 __% 提升至 __%。"

后者的每个词都能被追问，也都接得住追问——"为什么是 RRF 不是加权融合""X 到 Y 的测试集怎么建的"，每一步你都有第 5、6 章的实战垫底。这就是"问题 → 决策 → 数字"结构的威力：它自带追问邀请函，而追问的方向全是你的主场。

推论（也是纪律）：**写不出数字的点，要么回去补做 eval，要么从简历上删掉。** 没做过的技术同理——写了 Kubernetes 就会被问调度原理，写了 LangChain 就会被问"和你手写的 ReAct 循环什么区别"，答不上比不写更减分。

### 1.2 每个项目准备三种讲法

同一个项目，按场合切换三种粒度：

| 版本 | 时长 | 内容 | 使用场景 |
| --- | --- | --- | --- |
| 电梯版 | 30 秒 | 问题 + 一个最亮的结果数字 | 自我介绍、"简单介绍下这个项目" |
| 架构版 | 5 分钟 | 整体架构图（能默画）+ 2-3 个关键取舍 | "详细讲讲这个项目" |
| 深挖版 | 不限时 | 任一组件的实现细节、踩过的坑、权衡过程 | 面试官往底层追问时见招拆招 |

三个版本的示范见第四节。两条练习纪律：

- 电梯版的 30 秒是**硬约束**——自我介绍超时是面试最常见的第一印象失分点，必须掐表练过，练到不看稿、不超速；
- 架构版的配套图要能**默画**：项目 2 的双链路图（阶段二 3.3）、项目 3 的生命周期时序图（阶段三 3.3）。面试时主动说"我画一下架构图"，主动权就在你手里了。

### 1.3 面试回答的分层递进策略

回答技术/项目问题的默认节奏：**先给结论和全貌，停住，等面试官挖，再下钻。**

- **第一层（默认）**：结论 + 一句话理由。"我用了混合检索，因为纯向量检索对错误码这类字面查询效果差。"
- **第二层（被追问时）**：机制。"向量检索语义匹配强但字面弱，BM25 正好互补，两路结果用 RRF 融合。"
- **第三层（继续深挖时）**：实现细节和数据。"RRF 里 k 取 60，融合后 recall@5 从 __% 提到 __%，eval 报告在这里。"

**反模式**：一上来讲实现细节。面试官 30 秒内抓不到全貌会失去耐心，而且你讲细了他反而无法确认你真懂全局。分层递进同时展示"能概括"和"能深入"两种能力——这正是高级工程师和背题选手的区别。

这个策略和前 13 章的知识组织方式天然匹配：每章的"本章地图"就是第一层，"概念详解"是第二层，"代码精讲"和真实数字是第三层。你已经在按这个结构学习了，面试只是把它说出来。还有一个隐藏好处：**停住等追问，等于把面试节奏交给对方的同时把方向留在了你的领地**——面试官的追问大概率落在你准备最深的区域。

### 1.4 STAR 法则：A（行动）占 60-70%

行为面试题（"讲一个你遇到的最难的问题"）按四步答：

- **S（Situation）情境**：背景一句话，不铺陈；
- **T（Task）任务**：你的职责和目标，一句话；
- **A（Action）行动**：你具体做了什么——**这是主体，占 60-70% 篇幅**，讲决策链条（"我先排除了 X，因为……然后怀疑 Y，用 Z 方法验证"），不是流水账；
- **R（Result）结果**：量化结果 + 你学到什么、之后怎么防复发。

常见错误：S/T 讲了两分钟，A 一句"然后我解决了"带过。面试官听的就是 A——你的判断过程。

以"SSE 流式静默失败"（阶段一注意事项 #9）为例，A 部分的骨架大约一分钟：

1. 锚定现象："流式接口返回 200，但前端一个字都渲染不出来"；
2. 排除法："先排除网络层——`curl` 能收到 `data:` 行，说明服务端在推"；
3. 定位手段："怀疑解析层，加日志发现 `content` 永远为空；对照协议发现 struct 的 json tag 写错了字段名，Unmarshal 静默忽略"；
4. 防复发："修复后补了'首个 delta 到达'的断言日志，同类静默失效以后十秒内能暴露。"

注意这个骨架里没有一句"我很努力"，全是可验证的动作——这才是 A 部分该有的信息密度。第五节的素材表会帮你给每道高频题都备一个这样的骨架。

### 1.5 开源的信号强度排序

简历上写"代码质量高、工程能力强"是**自述**，无法验证；一个公开的 GitHub repo 是**他证**，面试官可以直接看代码、commit 历史、issue 处理。信号强度从强到弱：

1. **被合并的知名项目 PR**（最强：陌生 maintainer 审核过你的代码）；
2. **自己带 CI/测试的开源 repo**（证明能独立交付完整软件）；
3. **简历上的项目描述**（最弱：全靠面试时口头验证）。

性价比策略：一个文档修正 / 示例补充 PR 可能只需几小时，但"某某知名项目 contributor"在简历上的辨识度远超同等时间投入的其他动作。当然，能修真 bug 更好。候选方向就用你教程里真实用过的工具链（LangChain-Go、MCP 官方 server 仓库、Vercel AI SDK 的文档/示例）——用过的项目，你才知道它哪里真的缺东西，PR 立意才站得住。

### 1.6 系统设计题五步法

系统设计是 Agent 岗面试的压轴题型，固定五步走，节奏自己控制：

1. **澄清需求**（3-5 分钟）：用户是谁、规模多大、核心场景、约束（延迟/成本/合规）。不澄清就动手是系统设计大忌。
2. **容量估算**（2-3 分钟）：QPS、数据量、存储量级。数字不需要准，需要**量级正确**——它决定后面选单机还是分布式、内存还是外存。
3. **高层架构**（5-8 分钟）：画出 3-5 个大方块和数据流向，讲清每条链路。这一步就是分层递进的第一层。
4. **关键取舍**：主动说出 2-3 个"我选了 A 没选 B，因为……"。取舍意识比任何单一正确答案都值钱。
5. **深入一两个组件**：让面试官选方向，或自己挑最有把握的下钻——讲你项目里真实做过的部分。

面试官的打分点其实就藏在这五步里：澄清看你是否鲁莽、估算看量级直觉、架构看全局观、取舍看工程判断力、深入看手上有没有真功夫。45 分钟的面试里前两步不要超过 8 分钟——时间花在取舍和深入上才产生区分度。

这套框架和本教程的学习路径同构：澄清需求 ≈ 读题，容量估算 ≈ 第 1、4 章的成本/数据量估算习惯，高层架构 ≈ 每章的本章地图，取舍 ≈ 每章的进阶拓展，深入组件 ≈ 代码精讲。第三节用两道真题演示完整流程。

## 三、实战：两道系统设计题精讲

> 两道题分别套项目 2、项目 3——**答案就是你自己的项目，底气来自真做过**。下面按五步框架给出踩分点清单，每个踩分点标注对应的教程章节；模拟时对照检查自己漏了哪一层。
>
> 模拟方法：掐表 45 分钟，白板或纸笔画图，全程出声（或录音）。结束后对照清单自评覆盖率，低于 80% 的行回链对应章节重读，三天后换一道题再模拟。

### 3.1 题一：设计一个企业知识库问答系统（套项目 2）

| 环节 | 踩分点 | 答案出处 |
| --- | --- | --- |
| 澄清需求 | 文档量级与类型（md/pdf/网页）、并发用户数、是否要求答案可溯源、数据更新频率、权限隔离（不同部门看到不同文档） | —（框架动作） |
| 容量估算 | 文档数 → chunk 数（×10-50）；QPS 决定检索是否内存暴力就够（<10 万不必上 HNSW）；每次问答的 token 构成与 embedding/LLM 成本 | [第 4 章](04-embedding-and-vector-search.md)、[第 1 章](01-llm-api-and-messages.md) 1.6 节 |
| 高层架构 | **写入/查询双链路必须分开讲**：写入 = 解析 → chunking → embed → 入库；查询 = query（可选改写）→ embed → 检索 → 拼 prompt → 带引用生成。能默画这条双链路图 | [第 5 章](05-rag-pipeline.md)、阶段二 3.3 时序图 |
| 关键取舍 | ① chunk 策略：固定窗口 vs 按结构切，大小与 overlap 的权衡（第一调参位）；② 纯向量 vs 混合检索（字面查询短板，RRF 融合）；③ top-k 与阈值：召回与噪声的权衡；④ 是否上 rerank：成本换精度 | [第 5 章](05-rag-pipeline.md)（混合检索/rerank 见其进阶部分） |
| 深入组件 | **主动给出 eval 闭环**：测试集怎么建、recall@k / MRR 怎么算、bad case 三板斧（检索不到/答非所问/编造）各自怎么定位、调优前后数字对比 | [第 6 章](06-memory-and-evals.md) |
| 加分 | 流式 UI 与可点击引用卡片、权限过滤（元数据 where）、增量更新与删除的一致性、防幻觉 prompt 设计 | [第 7 章](07-fullstack-kb-agent.md)、第 5 章 |

开场 60 秒示范（澄清需求环节）："动手前我想先确认几点：文档量级是几千篇还是几百万篇？类型是纯 Markdown 还是混有 PDF 扫描件？并发用户大概多少？答案是否必须可溯源到原文？有没有部门级的权限隔离？"——五个问题不到一分钟，但每个答案都对应后面一个架构决策：量级决定检索方案，类型决定解析链路，可溯源决定引用设计，权限决定元数据过滤。

讲这道题最易犯的错是直接跳到"我会用某某向量库"——那是背题选手的路径。你的路径是：双链路画图 → 四个取舍摆上桌 → eval 闭环收尾，每一环都有项目 2 的代码和数字背书。

### 3.2 题二：设计一个多 Agent 任务执行平台（套项目 3）

| 环节 | 踩分点 | 答案出处 |
| --- | --- | --- |
| 澄清需求 | 任务类型（长/短任务）、是否需要人工审批节点、任务规模与并发度、失败容忍度 | —（框架动作） |
| 容量估算 | 并发任务数、单任务的 LLM 调用次数与 token 成本、状态存储量级 | 第 1 章成本核算 + [第 12 章](12-observability-and-mcp.md)（成本归因） |
| 高层架构 | 编排引擎（planner → worker → critic）+ 任务状态持久化 + 实时看板（SSE 推送状态）三个大方块 | [第 10 章](10-orchestrator-planner-worker-critic.md)、阶段三 3.3 时序图 |
| 关键取舍 | ① 为什么拆多 agent 而不是单 agent 加工具（职责隔离 vs 协调开销）；② 并发控制：errgroup + semaphore 限流、context 预算分级；③ 状态机设计：状态枚举与迁移；④ **checkpoint 恢复**：进程挂了从哪一步续跑，幂等性怎么保证 | 第 10 章；[第 8 章](08-go-concurrency-and-worker-pool.md)；[第 9 章](09-task-persistence-and-recovery.md) |
| 深入组件 | HITL：哪些节点必须人审、审批如何阻塞/恢复状态机（事件驱动而非挂起 goroutine）；可观测：trace 怎么串起跨 agent 调用链、成本归因到任务维度 | [第 11 章](11-human-in-the-loop.md)；[第 12 章](12-observability-and-mcp.md) |
| 加分 | 任务重试退避（尊重 Retry-After + jitter 防惊群）、部分失败隔离（一个 worker 挂了不影响整体）、看板实时性取舍（轮询 vs SSE 推送） | 第 8 章；[第 13 章](13-server-sse-dashboard.md) |

容量估算示范："假设平台同时跑 100 个任务，每个任务平均 10 个子任务、每个子任务 3 次 LLM 调用、单次约 5K token——峰值并发下 LLM 调用达到几十 QPS 量级，semaphore 限流和 429 退避就必须当成一等公民设计（第 8 章）；状态每任务 KB 级，SQLite/Postgres 起步足够（第 9 章）。"数字粗糙没关系，展示的是"估算 → 架构决策"的推导链条。

这道题的题眼是取舍①——"什么时候**不该**上多 agent"。能主动说"单 agent 加工具能解决的我不会拆，多 agent 是用状态一致性、成本、调试复杂度换职责隔离"（阶段三 3.1 Q1），面试官就知道你不是为炫技而拆。

### 3.3 与"只看过教程"的候选人拉开差距的三个点

两道题的框架谁都能背，拉开差距的是这些只有真做过才有的东西：

1. **eval 数字**。"recall@5 从 X% 提到 Y%"和"我会调优 RAG"是两种完全不同的可信度。数字从你自己的 eval 报告里取真值（第 6 章练习产出）。
2. **故障演练记录**。项目 3 的 checkpoint 不是背出来的——你真的 kill 过进程、看重启后任务从断点续跑（第 9 章）。说一句"我实测过崩溃恢复"胜过十句"支持断点续传"。
3. **真实踩坑**。SSE delta tag 写错静默失败、重试 off-by-one、APIError 接线漏接导致 401 被重试（阶段一注意事项 #9-14）——每个坑都是一个 STAR 故事的 A 部分。

## 四、简历实战：三个项目示范段落

> 结构统一为"问题 → 架构决策 → 量化结果"。**段落中的 `__` 是占位符，投递前必须从 eval 报告 / 实测数据里取真实数字填入**——写不出数字的项目段落等于没写（1.1 节的纪律）。每段附"电梯版一句话"，用于自我介绍和口头开场。

> 数字从哪来：recall@k / MRR 出自项目 2 的 eval 脚本输出（第 6 章练习 8-9）；token 成本出自 `Usage` 累计与 trace 报表（第 1 章进阶 3.4、第 12 章）；延迟数字出自实测。现在就缺数字的，回到 30 天行动表第 1 周补齐。

### 项目 1：`mini-agent/` —— Go 迷你 Agent 框架

> 独立设计并实现零框架依赖的 LLM Agent 内核（Go + DeepSeek API）：手写 ReAct 循环、Function Calling 协议与工具调度，支持 SSE 流式输出（含 tool_calls 分片聚合）、指数退避重试与上下文压缩；内置安全工具层（表达式求值、HTTP 抓取截断、文件读写路径防护）。完整覆盖单测，核心机制均有文档化沉淀。

电梯版一句话："我用 Go 从零手写了一个 Agent 框架——ReAct 循环、工具协议、流式、重试、压缩全自己实现，所以市面上的框架对我没有黑盒。"

### 项目 2：`stage-02-kb-agent/` —— 全栈知识库 RAG 问答系统

> 面向企业文档问答场景，实现端到端 RAG 系统（Next.js + Vercel AI SDK）：文档上传 → 结构化 chunking → bge-m3 embedding → 向量检索 → 流式生成带可跳转引用的回答。建立 eval 测试集驱动调优：通过混合检索与 chunk 参数调整，将检索 recall@5 从 __% 提升至 __%，MRR 从 __ 提升至 __；沉淀 __ 条 bad case 分析与调优报告。

EN keywords: `RAG` / `chunking strategy` / `hybrid retrieval (vector + BM25)` / `recall@k / MRR` / `citation-grounded generation` / `eval-driven tuning`

### 项目 3：多 Agent 任务系统 —— Go 编排引擎 + TS 实时看板

> 设计多 Agent 任务编排引擎（Go）：planner/worker 角色拆分，基于状态机的任务生命周期管理，支持 checkpoint 断点恢复与 goroutine 并发编排；内置 human-in-the-loop 审批节点与 trace 可观测（成本归因到任务维度）；配套 TypeScript 实时看板（SSE 推送）展示任务执行全过程。

电梯版一句话："我设计了一个多 Agent 任务平台：planner/worker 编排、状态机 checkpoint 崩溃恢复、人工审批、全链路 trace，Go 引擎加 TS 实时看板。"

EN keywords: `multi-agent orchestration` / `state machine` / `checkpoint recovery` / `human-in-the-loop` / `observability / tracing` / `cost attribution`

## 六、求职常见坑

1. **"熟悉 LLM"不如"把 recall@5 从 X 提到 Y"**：简历上一切"熟悉/了解/精通"类虚词都要替换成"做了什么 + 数字"（1.1 节的纪律，这里再强调一次，因为它是最多人栽的一条）。
2. **没做过的技术别写，写了必被深挖**：面试官的默认动作是挑简历上最显眼的词往底层问。写了 LangChain 就会被问"和你手写的 ReAct 循环什么区别"——答不上比不写更减分。
3. **不录音的模拟面试等于没模拟**：自以为讲清了和实际讲清了是两回事。回听三问见第二节末尾。
4. **开源 repo 的 README 决定第一印象**：三件套缺一不可——架构图（10 秒看懂是什么）、CI 徽章（证明能跑）、快速开始（5 分钟跑起来）。英文 README 是底线；commit 历史别是单次上传，真实迭代过程本身就是信号。
5. **海投不如精投 + 内推**：海投的简历筛选通过率低且消耗心态。正确姿势：目标公司分级 → 每级找内推渠道 → 针对 JD 微调项目段落措辞（见第七节动作 6）。
6. **一面挂在高频题上最亏**：系统设计靠积累，但第二节索引表里那些题是有标准答案的——这种分必须拿满，自测正确率不到 90% 不要开始投递。

- 每个项目三种讲法（30 秒 / 5 分钟 / 深挖）；回答问题分层递进：先结论，停住，等追问再下钻。
- STAR 里 A 占 60-70%，讲决策链条，不讲流水账。
- 开源信号：被合并的知名项目 PR > 自己带 CI/测试的 repo > 简历形容词。
- 系统设计五步法：澄清 → 估算 → 架构 → 取舍 → 深入；答案就是你的项目，差距在 eval 数字、故障演练、真实踩坑。
- 题库不背新答案：按第二节索引回到教程章节和阶段文档，录音自测是唯一诚实的裁判。

没有下一章了——接下来 30 天，把"学过"变成"拿到"。

| 周 | 目标 | 具体动作 |
| --- | --- | --- |
| 第 1 周 | 补齐技术债，取出真值数字 | 补完所有未完成的 `TODO(练习N)`；跑通项目 2 eval 脚本，把 recall@5 / MRR 真值记入调优报告；项目 3 实测一次崩溃恢复并记录 |
| 第 2 周 | 简历 + 开源 | 简历 v1 定稿（双语、量化数字填真）；mini-agent 开源上线（README 三件套）；发出第一个外部项目 PR |

每周日的固定动作：对照第八节 checklist 更新状态，把下周计划写进阶段四文档的任务清单。节奏感比强度重要——这 30 天是求职，也是最后一次用项目管理的方式管理自己。

执行状态维护在 [阶段四文档](../stages/stage-04-job-hunting.md) 第六节的任务清单里——本章负责"怎么打"，它负责"打到哪了"。

30 天后无论结果如何，回到第八节的总 checklist 复盘：拿到 offer，教程使命完成；没拿到，转化漏斗会告诉你短板在简历、一面还是终面，对应章节永远在这里等你回链。

祝面试顺利。
