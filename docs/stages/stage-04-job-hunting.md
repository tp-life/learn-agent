## 二、核心概念（必须能脱稿讲出来）

### 1. 简历项目段落的黄金结构：问题 → 架构决策 → 量化结果

每个项目用三句话讲清楚：

- **问题**：解决什么真实痛点（一句话，让非专家也能懂）；
- **架构决策**：关键的技术取舍及原因（1-2 个，体现判断力而不是堆砌）；
- **量化结果**：可度量的数字（recall@5、p99 延迟、token 成本下降比例……）。

**反例**："熟悉 LangChain、向量数据库、LLM、RAG、Agent……"——罗列技术栈 = 告诉面试官"我背过名词"。面试官要的是"你做过什么、怎么做决策的、效果如何"。

每个项目准备**三种讲法**：

| 版本 | 时长 | 内容 | 使用场景 |
| --- | --- | --- | --- |
| 电梯版 | 30 秒 | 问题 + 一个最亮的结果数字 | 自我介绍、"简单介绍下这个项目" |
| 架构版 | 5 分钟 | 整体架构图 + 2-3 个关键取舍 | "详细讲讲这个项目" |
| 深挖版 | 不限 | 任一组件的实现细节、踩过的坑、权衡过程 | 面试官追问到底层时见招拆招 |

### 2. STAR 法则在行为面试中的运用

行为面试题（"讲一个你遇到的最难的问题"）按四步答：

- **S（Situation）情境**：背景一句话，不铺陈；
- **T（Task）任务**：你的职责和目标，一句话；
- **A（Action）行动**：你具体做了什么，**这是主体，占 60-70% 篇幅**，讲决策过程而不是流水账；
- **R（Result）结果**：量化结果 + 你学到什么。

常见错误：S/T 讲了两分钟，A 一句"然后我解决了"带过。面试官听的是 A——你的判断链条。

### 3. 开源作为信号：为什么 repo 比形容词值钱

简历上写"代码质量高、工程能力强"是**自述**，无法验证；一个公开的 GitHub repo 是**他证**，面试官可以直接看代码、commit 历史、issue 处理。信号强度排序：

1. 给知名项目提过并被合并的 PR（最强：陌生人审核过你的代码）；
2. 自己的开源项目，带英文 README + CI + 测试（证明能独立完成可交付的软件）；
3. 简历上的项目描述（最弱：全靠面试时口头验证）。

给知名项目提 PR 的性价比：一个文档修正 / 示例补充 PR 可能只需几小时，但"LangChain-Go contributor"在简历上的辨识度远超同等时间投入的其他动作。当然，能修真 bug 更好。

### 4. 面试讲解的"分层递进"策略

回答技术/项目问题时：**先给结论和全貌，停住，等面试官挖，再下钻**。

- 第一层（默认）：结论 + 一句话理由。"我用了混合检索，因为纯向量检索对错误码这类字面查询效果差。"
- 第二层（被追问时）：机制。"向量检索语义匹配强但字面弱，BM25 正好互补，两路结果用 RRF 融合。"
- 第三层（继续深挖时）：实现细节和数据。"RRF 里 k 取 60，融合后 recall@5 从 __% 提到 __%，eval 报告在这里。"

**反模式**：一上来讲实现细节。面试官 30 秒内抓不到全貌会失去耐心，而且你讲细了他没法确认你真的懂全局。分层递进同时展示了"能概括"和"能深入"两种能力。

### 5. 系统设计题答题框架

固定五步走，节奏自己控制：

1. **澄清需求**（3-5 分钟）：用户是谁、规模多大、核心场景是什么、有哪些约束（延迟/成本/合规）。不澄清就动手是系统设计大忌。
2. **容量估算**（2-3 分钟）：QPS、数据量、存储量级。数字不需要准，需要量级正确——它决定后面选单机还是分布式、内存还是外存。
3. **高层架构**（5-8 分钟）：画出 3-5 个大方块和数据流向，讲清每条链路。这一步对应"分层递进"的第一层。
4. **关键取舍（trade-off）**：主动说出 2-3 个"我选了 A 没选 B，因为……"。取舍意识比任何单一正确答案都值钱。
5. **深入一两个组件**：让面试官选方向，或自己挑最有把握的下钻（讲自己项目里真实做过的部分）。

### 3.2 系统设计题两道（答题骨架：面试官视角的踩分点清单）

> 不是完整答案，是**踩分点清单**——模拟时对照检查自己漏了哪一层。两道题分别套项目 2、项目 3，答案就是你自己的项目，底气来自真做过。

**题一：设计一个企业知识库问答系统**（套项目 2 `stage-02-kb-agent/`）

| 环节 | 踩分点 |
| --- | --- |
| 澄清需求 | 文档量级与类型（md/pdf/网页）、并发用户数、是否要求答案可溯源、数据更新频率、权限隔离（不同部门看到不同文档） |
| 容量估算 | 文档数 → chunk 数（×10-50）；QPS 决定检索是否够用内存暴力；embedding/LLM 调用成本估算（每次问答的 token 构成） |
| 高层架构 | **写入/查询双链路**必须分开讲：写入 = 解析 → chunking → embed → 入库；查询 = query（可选改写）→ embed → 检索 → 拼 prompt → 带引用生成。画出两个阶段文档 3.3 那张图 |
| 关键取舍 | ① chunk 策略：固定窗口 vs 按结构切，大小与 overlap 的权衡（第一调参位）；② 纯向量 vs 混合检索（字面查询短板）；③ top-k 与阈值：召回与噪声的权衡；④ 是否上 rerank：成本换精度 |
| 深入组件 | 主动给出 eval 闭环：测试集怎么建、recall@k / MRR 怎么算、bad case 三板斧（检索不到/答非所问/编造）各自怎么定位、调优前后数字对比——**这是与"只看过教程"的候选人拉开差距的点** |
| 加分 | 权限过滤（元数据 where）、增量更新与文档删除的一致性、防幻觉 prompt 设计、引用可点击跳回原文 |

**题二：设计一个多 agent 任务执行平台**（套项目 3）

| 环节 | 踩分点 |
| --- | --- |
| 澄清需求 | 任务类型（长任务/短任务）、是否需要人工审批节点、任务规模与并发度、失败容忍度 |
| 容量估算 | 并发任务数、单任务的 LLM 调用次数与 token 成本、状态存储量级 |
| 高层架构 | 编排引擎（planner → worker → critic/handoff）+ 任务状态持久化 + 实时看板（TS 前端，SSE/WebSocket 推送状态） |

| 深入组件 | HITL（human-in-the-loop）：哪些节点必须人审、审批如何阻塞/恢复状态机；可观测性：trace 怎么串起一个任务跨多个 agent 的调用链、成本归因到任务维度 |
| 加分 | 任务重试的退避策略、部分失败（一个 worker 挂了不影响整体）、看板实时性的实现取舍（轮询 vs 推送） |

## 四、注意事项（易踩坑）

> 随求职推进逐条累积。预置 5 条：

1. **"熟悉 LLM"不如"做过 RAG 并把 recall@5 从 X 提到 Y"**：简历上一切"熟悉/了解/精通"类虚词都要替换成"做了什么 + 数字"。写不出数字的点，要么回去补做 eval，要么从简历上删掉。
2. **没做过的技术别写，写了必被深挖**：面试官的默认动作是挑简历上最显眼的词往底层问。写了 Kubernetes 就会被问调度原理，写了 LangChain 就会被问"和你手写的 ReAct 循环什么区别"——答不上比不写更减分。
3. **模拟面试要录音回听**：自以为讲清了和实际讲清了是两回事。回听时对照三点：有没有先给结论（分层递进）、有没有超时（电梯版 30 秒是硬约束）、有没有"嗯/然后"填充词。
4. **开源 repo 的 README 决定第一印象**：三件套缺一不可——架构图（10 秒看懂是什么）、CI 徽章（证明能跑）、快速开始（5 分钟跑起来）。英文 README 是底线；commit 历史别是单次上传（体现真实迭代过程）。
5. **海投不如精投 + 内推**：海投的简历筛选通过率低且消耗心态。正确姿势：目标公司分级（冲刺/匹配/保底）→ 每级找内推渠道（脉脉/LinkedIn/技术社群）→ 针对 JD 微调项目段落的措辞侧重（Go 岗突出项目 1/3 的底层，TS 岗突出项目 2 的全栈）。
