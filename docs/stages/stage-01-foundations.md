## 一、这个阶段在学什么

不用任何框架，手写一个迷你 Agent（Go + DeepSeek API），把 LLM 应用的四个核心机制吃透：

1. messages 协议与 prompt 工程
2. Function Calling（工具调用）
3. ReAct 循环（agent 内核）
4. 流式输出、token 与成本控制

## 二、核心概念（必须能脱稿讲出来）

### 1. Agent 的本质是一个循环

```
for {
    resp = LLM(历史消息, 工具列表)
    if resp 没有 tool_calls → 返回最终答案
    执行工具 → 结果以 role=tool 追加回历史 → 继续循环
}
```

市面上的 agent 框架（LangChain、AutoGen……）内核都是这个循环 + 各自的外围抽象。
代码位置：`mini-agent/internal/agent/agent.go`。

### 2. Function Calling：模型只"请求"，不"执行"

- 模型输出的是**文本协议**（工具名 + JSON 参数），真正的执行在我们的代码里。
- 因此工具的 `args` 是**不可信输入**：可能畸形、缺字段、超长——必须校验。
- 工具三要素是"给模型看的说明书"（Name/Description/Schema），说明书质量直接决定模型选对工具、传对参数的概率。

### 3. messages 四角色协议

| 角色 | 职责 |
|---|---|
| system | 立规矩，全会话一条，放最前 |
| user | 用户输入 |
| assistant | 模型回复；想调工具时 ToolCalls 非空 |
| tool | 工具结果，必须用 ToolCallID 回指对应的 assistant 调用 |

### 4. 对话历史就是状态

LLM API 是无状态的——每轮请求都把全部历史重发一遍。agent 的"记忆"全靠客户端维护 `messages` 数组。

## 三、知识梳理（复习资料）

> 目标：只看本节，就能通过本阶段相关的面试提问。

### 3.1 自问自答考点清单

**Q1：什么是 Function Calling？它和"模型执行代码"是一回事吗？**
不是。Function Calling 是模型在响应中返回一个结构化请求（工具名 + JSON 参数），由客户端代码真正执行，再把结果以 `role=tool` 消息喂回模型。模型自始至终只生成文本，从不执行任何代码。这也是工具层必须做安全校验的原因。

**Q2：ReAct 循环的终止条件有哪些？**
① 模型返回的消息没有 tool_calls（认为任务完成，正常终止）；② 达到 MaxSteps 上限（保险丝，异常终止）；③ API 不可恢复错误（如鉴权失败）。生产中还常有 ④ 超时熔断和 ⑤ 成本预算上限。

**Q3：为什么 agent 循环里通常用非流式请求？**
因为需要拿到**完整的** tool_calls 才能决定下一步动作（调哪个工具、传什么参数）。流式下 tool_calls 是分片到达的，得先缓冲拼完整才能用——流式的价值在最终答案返回给用户的环节，不在循环内部。

**Q4：对话历史无限增长怎么办？**
三板斧：① 滑动窗口（只留最近 N 轮，简单粗暴）；② 摘要压缩（让 LLM 总结早期历史替换成一条 system/summary 消息，保留关键信息）；③ 重要事实抽取到结构化存储（长期 memory）。选型取决于会话长度和任务类型。

**Q5：temperature 在 agent 场景怎么设？为什么？**
偏低（0~0.3）。agent 的核心诉求是工具选择准确、参数格式稳定，而不是文采；高温度会增加 JSON 畸形和工具乱选的概率。最终面向用户的润色环节才考虑调高。

**Q6：工具执行失败了应该怎么处理？**
不要直接抛给用户。把错误信息（含原因）以 tool 消息喂回模型，让它换参数/换工具自我恢复。只有达到重试上限或安全类错误才终止并告知用户。

**Q7：工具的 Description 怎么写才好？**
公式：用途 + 使用时机 + 反面提示（什么时候不要用）。多个工具职责重叠时模型会乱选，第一手段是改 Description 划清边界，而不是加代码逻辑。

**Q8：一次响应里可以有多个 tool_calls 吗？怎么处理？**
可以（并行工具调用）。客户端依次（或并发）执行，每个结果单独发一条 role=tool 消息，用各自的 ToolCallID 回指。注意全部执行完再发起下一轮 LLM 请求。

**Q9：system prompt 放几条？放哪里？**
一条，放 messages 数组最前面。多轮对话中每一轮 API 请求都要带上——API 无状态，不存在"设过一次就生效"。

**Q10：token 成本怎么估算和控制？**
成本 ≈ (prompt tokens + completion tokens) × 单价，prompt 占大头（历史每轮全量重发）。控制手段：工具结果截断、历史压缩、用 DeepSeek 的上下文缓存（重复前缀命中缓存大幅降价）、限制 MaxSteps。

### 3.2 易混淆概念对比

| 概念 A | 概念 B | 区别要点 |
|---|---|---|
| tool_calls（assistant） | role=tool 消息 | 前者是模型发起的调用**请求**，后者是代码执行后回喂的**结果**，靠 ToolCallID 配对 |
| 流式（SSE） | 非流式 | 流式逐 token 返回、首字延迟低，适合最终答案；非流式一次拿全，适合循环内决策 |
| 无状态 API | 会话状态 | API 本身不记任何历史；多轮对话 = 客户端每轮重发全部 messages |
| system prompt | user prompt | system 立规矩（优先级高、全程有效），user 是当前任务输入；注入攻击常利用 user 内容篡改指令，敏感规则只放 system |
| 温度 temperature | top_p | 都控随机性，一般只调一个；agent 场景低 temperature 即可，不必动 top_p |
| MaxSteps | 超时 | MaxSteps 防"逻辑死循环"（反复调工具），超时防"单次调用卡死"，两者都要 |

### 3.3 ReAct 循环时序图（一次多步工具调用）

```
用户          CLI/Agent           LLM API            工具
 │  "357*482?"    │                 │                 │
 │───────────────>│                 │                 │
 │                │ messages+tools  │                 │
 │                │────────────────>│                 │
 │                │  tool_calls:    │                 │
 │                │  calculator(..) │                 │
 │                │<────────────────│                 │
 │                │─────────────────────────────────> │
 │                │              执行 "357*482" = 172074
 │                │<───────────────────────────────── │
 │                │ 追加 role=tool 结果，再次请求       │
 │                │────────────────>│                 │
 │                │  无 tool_calls， │                 │
 │                │  最终答案文本    │                 │
 │  "172074"      │<────────────────│                 │
 │<───────────────│                 │                 │
```

要点：每轮请求都带**全量历史**；assistant 的 tool_calls 消息和 tool 结果消息成对追加。

### 3.4 一句话记忆卡片

- Agent = LLM + 工具 + 循环，循环是本体，框架是包装。
- 模型是"动嘴的"，代码是"动手的"；两者之间的协议就是 tool_calls。
- 历史即状态：你想让模型"记得"什么，就得在每轮请求里带什么。
- 工具说明书（Description/Schema）是 prompt 工程，不是文档负担。
- 所有进入循环的外部内容（工具参数、工具结果、网页文本）都是不可信数据。

## 四、注意事项（踩过的坑 & 易错点）

1. **assistant 含 tool_calls 的消息必须原样放回历史**，否则后续 role=tool 消息失去对应关系，API 直接报错。
2. **工具报错不要抛给用户**：把错误文本喂回给模型，它通常能换参数自我恢复——agent 鲁棒性的关键一招。
3. **模型会编造不存在的工具名**，dispatch 层要返回错误而不是 panic（`Registry.Call` 已处理）。
4. **工具结果必须有长度上限**：`http_fetch` 默认截断 8KB，否则一条结果烧掉几万 token 还挤爆上下文。
5. **agent 场景用低 temperature（0.3）**：减少发散，工具参数更稳定。
6. **必须设 MaxSteps 保险丝**：模型可能反复调工具停不下来，死循环就是烧钱循环。
7. **`go/types.Eval` 对无值表达式（如 `println(1)`）返回 err==nil 但 Value==nil**，直接 `.String()` 会 panic——已修复并加了测试。
8. embedding 返回数组**顺序要按 index 归位**，不能假设与输入顺序一致（阶段二用）。
