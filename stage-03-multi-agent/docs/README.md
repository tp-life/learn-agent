## 本练习在学什么

阶段三的最后一个练习不写代码，写**两份文档**。目的有两个：

1. **简历/面试素材**：阶段验收标准要求"能讲清为什么这样拆 agent、失败如何处理"。
   讲得清的前提是写得清——把口头表达先落成文字，按"问题 → 架构 → 量化结果"的
   简历口径组织，面试时直接脱稿。
2. **工程习惯**：真实团队里架构文档与故障演练（chaos drill / game day）报告是
   生产系统的标配产物。故障演练的价值不在"系统没挂"，而在**把设计文档里的
   每一条容错声明变成一条实测记录**——声明了崩溃恢复，就要真的 kill 一次进程看结果。

## 要交付的两份文档

在本目录新建：

### 1. `architecture.md` —— 架构文档

必须覆盖的大纲（顺序可调，条目不可缺）：

1. **系统总览图**（Mermaid）：用户/看板 → HTTP/SSE API → orchestrator →
   planner/pool/worker → critic/hitl → SQLite checkpoint → Langfuse trace，
   一张图说清数据流与控制流。
2. **为什么这样拆 agent**：先讲"能单 agent 就别多 agent"与三个撞墙信号
   （context 膨胀 / 工具选择准确率 / 职责混杂），再讲为什么选
   planner-worker + critic 叠加而不是 handoff / swarm（教程第二节第 1/2 条口径）。
3. **状态机与 checkpoint 设计**：状态图、每步落盘的时机与内容、幂等键、
   崩溃恢复流程（重启后怎么找回任务、怎么跳过已完成子任务）。
4. **失败处理**：失败四件套（重试/幂等/降级/死信）在本系统的落点 +
   LLM 输出校验（planner 计划过 schema 才进状态机）。
5. **并发设计**：errgroup + semaphore 限流 + context 超时预算分层。
6. **成本设计**：模型分级、critic 双重熔断、token 核算到子任务。
7. **可观测**：trace/span 层级与 agent 层级的对应关系，成本数据从哪来。
8. **取舍与已知局限**：诚实写——同步编排 vs 事件驱动、SSE 推送方式、
   SQLite 单机的扩展边界等。局限写得越诚实，文档越可信。

### 2. `failure-drills.md` —— 故障演练报告

五个演练，每个按固定五段写：**目的 / 步骤（真实可跑的命令）/ 预期 / 实际结果 / 结论**。

| # | 演练 | 对应机制（练习） |
| --- | --- | --- |
| 1 | 崩溃恢复：任务跑到一半 kill 进程 → 重启续跑 → 已完成子任务不重复执行 | 状态机 + checkpoint + 幂等键（练习2/3），可用 hitl-demo 实际操作 |
| 2 | 人工审批：高风险子任务暂停 → approve / reject 两条路径 | HITL 审批闸 + 一次性放行令牌（练习5） |
| 3 | 限流 / 部分失败：worker 部分失败不影响整体汇总 | pool 部分失败语义（练习1）+ 编排器汇总（练习3） |
| 4 | 预算熔断：token 预算耗尽任务 failed | critic 双重熔断之预算熔断（练习4） |
| 5 | planner 输出非法 JSON：schema 校验拦截 + 带反馈重试 | ValidatePlan + 重试（练习3） |
